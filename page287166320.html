1.2.5. Требования сервиса

В соответствии с Регламентом по передаче сервисов на поддержку часть работ для последующей успешной передачи на сервис необходимо выполнить на этапе Discovery.

Модель здоровья и мониторинг заполняет Сервис-менеджер, который должен быть подключен с момента Discovery. Если в результате проекта появляется новая ИТ система, необходимо создать соответствующую запись во всех каталогах (см. Как создать новую ИТ систему ниже).


Цель этапа:

Фиксировать требования сервиса. Получить оценку стоимости сопровождения и реализации требований сервиса, запланировать ресурсы Сервис-менеджеров (внутренний или внешний)

Роли этапа:

Сервис-менеджер, Руководитель проекта, Бизнес-аналитик, Архитектор решений, Менеджер развития практик сервисного подхода в ИТ

Условия на вход:

  1. Оформлены бизнес-требования, важно в первую очередь заполнить нефункциональные требования, HLD.

Шаги процесса:

  1. Лидер команды оценки отправляет ссылку на пространство проекта с заполненными требованиями Сервис-менеджеру (email)
  2. Лидер команды оценки организует встречу с Сервис-менеджером домена, Solution architect, Бизнес-аналитиком
  3. Лидер команды оценки дополняет бизнес-кейс данными по оценке
  4. Лидер команды оценки совместно с Сервис-менеджером Заполнить TTS в части артефактов, которые готовы на момент предпроекта, прикрепить заполненный документ к пространству проекта
  5. Сформулировать рекомендации по маршрутизации организации процесса поддержки (1, 2, 3 линии поддержки) и дополнить бюджет проекта на доработки маршрута процесса поддержки в OMNI
  6. Запланировать ресурс на поддержку (внутренний/ внешний, существующий/ новый), если необходимо - организовать найм, дополнить бизнес-кейс, бюджет проекта.
  7. Если в результате проекта будет создана ИТ система, необходимо создать новую запись, подробнее Как создать новую ИТ систему.

Результаты этапа:

  1. Получена оценка стоимости сопровождения
  2. Получена оценка стоимости участия Сервис-менеджера в проекте (в FTE)
  3. Заполнен TTS
  4. Получены рекомендации по маршрутизации организации процесса поддержки (1, 2, 3 линии поддержки) от Сервис-менеджера:
    • маршрут заявок в OMNI
    • форма на портале в OMNI
    • SLA для заявок
  5. Бюджет проекта дополнен суммой на доработку маршрутов поддержки в OMNI
  6. Принято решение о том, каким ресурсом будет осуществляться поддержка по завершению проекта, при необходимости дополнен бизнес-кейс, бюджет проекта.

Как создать новую ИТ систему

  1. Руководитель проекта направляет запрос (email) Архитектору решений - создать запись о новой ИТ системе в каталоге Arch tool.
  2. После того, как запись в Arch tool создана Архитектором решений - РП формирует заявку в Simpleone для создания записи о новой ИТ системе в прочих каталогах (тип заявки "Создание карточки в CMDB").
  3. Заявку в Simpleone обрабатывает Менеджер развития практик сервисного подхода в ИТ (Неизвестный пользователь (andrey.alyushin) ), который проверяет наличие записи в Arch tool , далее создает запись в Simpleone и SAP.
  4. Менеджер развития практик сервисного подхода в ИТ (Неизвестный пользователь (andrey.alyushin) ) - направляет запрос в SD (email, пример на скриншоте ниже) для создания записи о новой ИТ системе в Wss Docs (уточнить, кто обрабатывает такой запрос и заводит в Wss Docs - Оганесян Максим дополнит позднее).
  5. Менеджер развития практик сервисного подхода в ИТ (Неизвестный пользователь (andrey.alyushin) ) направляет запрос (email) Шмырев Сергей  и  Касаткин Владислав  для создания записи в IBM.
  6. Результатом выполнения пунктов 1-5 являются записи о новой ИТ системе в каталогах Arch tool, Simpleone, Wss Docs, SAP, IBM.
