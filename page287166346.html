1. Общие рекомендации

Цели раздела

  1. Получить реалистичные и управляемые план-графики (расписания) проектов
  2. Возможность передать ответственность за задачи проектов от РП к конечным исполнителям
  3. Возможность защищать перед спонсором, заказчиками и руководителями проектов даты контрольных точек и конечный срок окончания проекта


Правила и рекомендации к планированию проектов

  1. Вовлечение исполнителей в сроки проекта:
    1. Планирование вместе с командами, чтобы набор задач был полным, зависимости - реальными, ожидания совпадали и было проще согласовывать конечное расписание
    2. Согласование (коммит под своими задачами) тимлидами и исполнителями
    3. Коммуникация на всю команду конечного базового плана
    4. Регулярное отслеживание сдвигов вместе с командой
  2. Иерархия задач на основе ценности для продукта. На верхнем уровне находится задача в виде важного релиза или большой функциональности.
  3. Задача назначается на конкретного члена команды проекта (ФИО, а не на группу), чтобы:
    1. Была персональная ответственность за конкретные задачи
    2. Помочь РП подрядчика управлять своей командой, если РП Ленты считает уровень управления командой подрядчика недостаточным
    3. Был достаточный уровень детализации задач для назначения персональной ответственности
  4. Зависимости задач, чтобы:
    1. Провести автопланирование задач при сдвиге сроков исполнения первых задач
    2. Автоматически рассчитывать критический путь проекта
    3. Через тип зависимости указать реальную логику зависимости задач
  5. Интуитивно понятная и полезная диаграмма Ганта с отображением необходимых данных сразу на диаграмме
  6. После согласования с командой и заказчиками версии план-графика задавать базовый план, чтобы:
    1. Был трекинг, на ком конкретно был сдвиг сроков
    2. Провести эффективное ретро после этапа или всего проекта
  7. Название задачи в план-графике должно:
    1. Отражать образ результата. Образ результата можно подробно писать в поле Заметки
    2. Быть однозначным (быть ближе к SMART)
  8. В план-графике должны быть задачи согласований. Или в явном виде в задаче для исполнителя должно быть прописано, что результат должен быть согласован с определенными ФИО
  9. В план-графике должны быть контрольные точки с четко описанным образом результата и методом приемки результата.
  10. Заложены буферы перед контрольными точками, чтобы в случаях сдвигов сроков по работам можно было "отъедать" буфер, а не сдвигать КТ
  11. Учет отсутствий:
    1. Настройка производственного календаря
    2. Учет отпусков исполнителе


Подходы к управлению проектом можно условно разделить на две большие группы: классические и гибкие*.

Классические методики (waterfall) управления проектами основываются на детальном планировании всех аспектов проекта до его старта и строгом следовании этому плану в течение всего жизненного цикла проекта.

Гибкие методы управления базируются на итеративном и адаптивном подходе к планированию и воплощению проекта с учётом постоянно изменяющихся условий и обратной связи от клиента.

*Также существует гибридный подход, когда основную разработку планируем по waterfall, а прочие работы гибко - подходит для RND-проектов.

В зависимости от выбранного подхода к управлению проекта, общие рекомендации для планирования перечислены ниже.


Релевантно для подхода waterfall:

Epic рекомендуется включать в структуру как подчиненную задачу к WBS "Выполнение проекта". Если поставок на продуктив несколько, кол-во Epic в структуре плана будет совпадать с кол-вом поставок.

Основные этапы реализации должны быть определены по каждому эпику через элемент WBS (формирование этапов через Epic является некорректным способом).

Типичные этапы проекта:

  • сбор требований
  • проектирование
  • реализация
  • функциональное тестирование
  • интеграционное тестирование
  • нагрузочное тестирование (опционально)
  • опытная эксплуатация
  • передача на поддержку
  • тиражирование и переход к промышленной эксплуатации

Для каждого этапа должны быть спланированы активности в виде task-non-dev (задача без разработки) или task (в случае задач по разработке), которые могут группироваться с использованием WBS.

Для каждого элемента типа task и task-non-dev обязательно должен быть назначен ответственный, который выполняет задачу - пустым поле "Исполнитель" оставлять нельзя.

Сроки для элементов плана в JIRA:

  1. Рекомендуется определять дату исполнения по всем типам задач (включая task и task-non-dev).
  2. По WBS и Epic дата исполнения обязательно должна быть определена.

Также рекомендуется использовать зависимости между задачами, при этом при изменении зависимости задач необходимо использовать автоматически рассчитываемые даты GanttStart и GanttFinish 
По task и task-non-dev -рекомендуется заводить задачи незадолго до старта исполнения, т.к. t2m по таким задачам считается от момента создания до решения.

2. Декомпозиция плана работ

Дополнить описанием процесса PI-планирования (PI планирование 2024 - IT Strategy - Confluence (lenta.com)) от Мягких Мария когда будет сформулирован подход.

PI-планирование - процесс совместной работы с командой Домена по планированию задач, который позволяет оптимизировать процессы и обеспечить согласованность действий команд в масштабах ИТ-дирекции.

Руководитель проекта не является обязательным участником встречи по PI-планированию, но важно, чтобы Руководитель домена обладал всей необходимой информацией для планирования бэклога Домена и кроссфункциональных задач.

Руководитель проекта обязательный участник регулярных встреч внутри Домена, где происходит планирование бэклога.
